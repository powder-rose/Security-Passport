# Раздел «Вопрос — ответ»

Самостоятельный тип контента: `/questions/` и `/questions/:slug/`. Блог и коммерческие URL сохраняются. Навигация доступна в общей шапке, мобильном меню и футере.

## Работа редактора

В админке откройте «Вопросы и ответы». Два материала из редакционного DOCX уже подготовлены со статусом «На проверке». Их даты публикации появятся при фактической публикации. Автоматическая нормативная или семантическая проверка не выполняется.

1. Заполните вкладку «Контент»: H1, slug, категорию, автора, краткий ответ и основной текст. Обложка необязательна; если используется, нужен alt. Редактор и загрузка изображений общие с блогом.
2. На вкладке «Связи» выберите основную опубликованную статью блога, при необходимости дополнительные статьи, коммерческую страницу и до четырёх опубликованных похожих вопросов. Флаг «Показывать вопрос в связанных статьях блога» включает обратную ссылку только для выбранных статей; по умолчанию выключен.
3. На вкладке «SEO» задайте Title и Description. Ключи остаются внутренними редакционными данными. Canonical обычно оставляйте пустым: система сформирует собственный URL. Ручной canonical допускается только на страницу вопроса основного домена.
4. После проверки нормативного содержания и пересечений по фактическим поисковым данным отметьте обе проверки. Изменение контента или основных связей в интерфейсе сбрасывает отметки. Проверки нельзя заменить разрешением предупреждений о дублях.
5. Откройте «Предпросмотр». Он требует действующей сессии, имеет noindex и не отправляет заявки из формы консультации.
6. Нажмите «Опубликовать» или задайте отложенное время. Статус общей очереди показывает завершение обновления HTML. Сохранение черновика опубликованного ответа не меняет его публичную версию.

Поиск CMS, фильтры категории/автора/статуса, архивирование, закрепление, настройки рубрики и справочник категорий доступны без программиста. Используемую категорию удалить нельзя; переименование обновляет связанные записи. История хранит последние 50 версий. Восстановление возвращает версию в черновик и требует повторных проверок.

Автосохранение срабатывает через 1,5 секунды после ввода. Версии автосохранений группируются с интервалом около минуты; ручные сохранения сохраняют предыдущую версию. Конкурирующие изменения одного материала защищены номером revision: устаревшее окно получает конфликт, без перезаписи свежей версии.

Запланированный материал заблокирован для редактирования до отмены расписания. Планировщик проверяет очередь раз в минуту и при старте backend. Перед публикацией повторно проверяет обязательные поля и доступность связанных материалов. При ошибке причина видна в списке CMS; материал возвращается на проверку, либо сохраняет прежнюю опубликованную версию.

## HTML, поиск и индексация

- Основной контент и метаданные опубликованных страниц формируются на сервере, до JavaScript. Каталог содержит первые 12 компактных карточек, без архива полных текстов в bootstrap.
- Поиск проверяет название, краткий и полный ответы опубликованных материалов. Категории и пагинация работают без перезагрузки; URL с параметрами имеют noindex и canonical на `/questions/`. Отдельные индексируемые страницы категорий не создаются.
- Sitemap обоих существующих форматов включает рубрику и только опубликованные индексируемые вопросы с собственным canonical. Черновики, предпросмотр и noindex исключены.
- При смене опубликованного slug старый адрес получает 301 на новый с сохранением параметров. Архивный ответ возвращает 404, даже если старый HTML ещё находится в release. Доступ к `/questions/slug/index.html` закрыт.
- Публичные ответы используют Article и BreadcrumbList, OG и Twitter-метаданные. lastmod/dateModified меняются при содержательных изменениях; работа с ключами, закреплением и техническое сохранение их не меняют.
- Яндекс Метрика использует действующий счётчик. Переход на услугу вызывает цель `question_service_click` с параметрами `question` и `service`. Просмотры раздела доступны по пути `/questions/`. Настройка отчёта/цели в личном кабинете Метрики выполняется отдельно.

Автоматический семантический анализ, расширенные SEO-отчёты и тематические страницы категорий относятся к P2 и в первый запуск не входят.

## Хранение и архитектура

`shared/contracts/questions.js` содержит общие контракты. `server/questions/` отвечает за валидацию, хранение, приватную/публичную версии и seed; `server/http/question-routes.mjs` — за API, авторизацию, выдачу HTML и расписание. Публичные компоненты находятся в `src/features/questions/`, страницы — в `src/pages/`. CMS использует `src/admin/features/questions/` и отдельные страницы.

Рабочий файл: `QUESTIONS_FILE`, по умолчанию `data/questions.json` относительно `PASSPORT_PROJECT_ROOT`/рабочей директории. Он не принадлежит release и не версионируется. При отсутствии файла backend читает два seed-материала, первая запись создаёт рабочий файл атомарно. Повреждённый файл не заменяется seed автоматически. В production существующий `PASSPORT_PROJECT_ROOT` сохраняет данные в постоянном checkout проекта; можно явно выбрать абсолютный persistent путь через `.env.server`.

В резервное копирование включите рабочий `questions.json` вместе с `articles.json` и общими uploads. Нельзя заменять runtime-файлы данными из пакета разработки. В приложенном пакете runtime-данных нет.

Публикация вопросов и блога использует одну существующую durable-очередь и `scripts/publish-blog.sh`: в изолированной сборке обновляются оба раздела и карты сайта, затем атомарно переключается release. Загруженные изображения и другие страницы сохраняются. Новые npm-зависимости не добавлены.

## Первый запуск после merge и успешного QG

Нужен полный deploy: новый раздел добавляет frontend, SSR и backend. Одного запуска старого `publish-blog.sh` недостаточно.

```bash
cd /var/www/pasport-bezopasnosty.ru/app/passport-security-base
git switch main
git pull --ff-only origin main
bash scripts/deploy-federal.sh
bash scripts/enable-questions-nginx.sh
```

Перед запуском сохраните рабочие данные штатным резервным копированием. `deploy-federal.sh` использует действующий механизм проверки и возврата предыдущей frontend/backend generation. Применение nginx отдельно: helper сверяет активный HTTPS-конфиг с исходной версией `e47af42`, сохраняет резервную копию, проверяет `nginx -t`, перезагружает и проверяет рубрику/404. При ошибке возвращает конфиг. Если активный конфиг изменялся вручную, helper остановится без изменений: перенесите только блоки `/questions` и `/questions/` из версионируемого конфига и проверьте `nginx -t`.

Nginx обязан направлять весь `/questions/` в backend, чтобы действовали архивирование и старые slug. HTML по-прежнему подготовлен prerender и читается из активного release. Простая статическая выдача с `try_files` обходит эти проверки.

После запуска проверьте `/questions/`, вход в CMS, закрытый предпросмотр обоих исходных ответов. Выполните ручные редакционные проверки, затем публикуйте. При первоначальном seed в sitemap находится только рубрика; после публикации двух материалов добавятся два URL с фактическими датами. Пересылать черновики в поисковые системы не нужно.

## Проверки разработчика

```bash
npm run format:check
npm run lint
npm run build
npm run test:e2e:run
```

`npm run build` выполняет QA, серверные тесты, client/SSR build, prerender и проверку результата. Browser-тесты требуют установленного Chromium Playwright, как в действующем CI. Новые тесты проверяют серверную выдачу, sitemap, закрытые черновики, HTML-санитизацию, revision/history, 301, даты, расписание, поиск, CMS и ширины 320–1440 px. Browser-сценарии используют временные данные и не публикуют исходные редакционные материалы.
