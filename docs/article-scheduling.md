# Публикации по расписанию и ежедневное письмо

## Работа редактора

В редакторе доступны «Черновик», «По расписанию» и «Опубликовать сейчас». Для расписания выберите будущую дату и время и заполните SEO Title и SEO Description, затем нажмите «Запланировать». Все даты и часы показываются по Москве (Europe/Moscow, UTC+3), независимо от часового пояса компьютера.

В меню «План публикаций» видны ближайший выход, ожидающие статьи, результат публикации и ошибки. Есть поиск по названию и категории, перенос времени, снятие с расписания и публикация сейчас. Снятая статья остаётся черновиком. Вкладка «История» показывает последний результат расписания каждой сохранённой статьи; это не неизменяемый журнал всех правок. «Нормативные документы» временно скрыты из меню, сами данные и маршруты сохранены.

Админку можно закрыть. Backend проверяет расписание каждые 15 секунд и при запуске. В выбранное время начинается обновление публичной версии: «Публикуется» означает процесс обновления, «Опубликовано» появляется после успешного завершения штатного publish-blog.sh. Это не обещание мгновенного переключения страницы ровно в указанную секунду: нужно время на prerender и проверку релиза. При остановленном VPS работа продолжится после его запуска.

До наступления времени статья имеет status=scheduled и недоступна в публичном API, HTML и картах сайта. Первое publishedAt устанавливается во время планового запуска, прежняя дата уже публиковавшейся статьи сохраняется. Сами статьи и файлы изображений не мигрируются. После перехода к публикации дальнейшее поведение публичного API и HTML соответствует штатной очереди публикации проекта.

Расписание хранится рядом со статьёй в data/articles.json в publicationSchedule. Записи без этого поля продолжают работать как раньше. Таймер и редактор используют одну очередь записи; перенос или отмена защищены от устаревшего состояния, а завершение старой задачи не перезаписывает новую. После перезапуска восстанавливаются просроченные задачи и разрыв между сохранением статьи и постановкой публикации в очередь. Ошибочные публикации не повторяются бесконечно: доступна явная повторная попытка. Обычное обновление публичной версии также включает уже готовые к публикации статьи и может завершить ранее ошибочную задачу.

## Ежедневное письмо

Получатель по умолчанию: mail@pasport-bezopasnosty.ru. Таймер systemd — каждый день в 09:00 Europe/Moscow. Письмо содержит статистику завершённых календарных дней (те же периоды и исключение ботов, что в админке), заявки за предыдущий день и приложения:

- statistics-YYYY-MM-DD.csv — посещения, заявки и конверсия;
- leads-YYYY-MM-DD.csv — полный список заявок за день с контактами;
- lead-details-YYYY-MM-DD.txt — сведения по каждой заявке, включая ответы анкеты и источник.

Обрабатываются формы, квиз и звонок из статьи. Ограничение административного списка в 500 заявок к отчёту не применяется. При количестве свыше 100 в теле письма показаны первые 100, полный список остаётся в приложениях. Даже день без заявок отправляется с явным сообщением. Отчёт не восстанавливает утраченную статистику старого VPS: используются реально сохранённые журналы нового сервера.

Успешная отправка сохраняется в data/daily-report.json; повторный штатный запуск за ту же отчётную дату пропускается. Сервис использует flock для защиты от параллельных запусков. Файл статуса и предпросмотр приватны. Статус на рабочем столе показывает наличие SMTP, фактическую активность/автозапуск systemd timer и последний результат отправки. Успешный ответ SMTP означает принятие письма сервером, а доставку в папку «Входящие» нужно подтвердить отдельно.

## Подключение на восстановленном VPS

Изменения сначала применяются к локальному репозиторию и проходят обычный пользовательский commit/PR/merge и деплой. Пакет не выполняет commit, push или установку на VPS автоматически. Существующие статьи, изображения, env и пароль не входят в пакет и не заменяются им. Локальные правки IP в scripts/deploy-federal.sh и scripts/publish-blog.sh, сделанные при восстановлении, сохраняйте: в исходном main пока остаётся старый адрес, и этот пакет эти файлы не меняет.

В приватном .env.server на сервере нужны реальные параметры исходящей почты:

```dotenv
SMTP_HOST=адрес-сервера-исходящей-почты
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=имя-пользователя-почты
SMTP_PASS=пароль-приложения-или-почты
DAILY_REPORT_EMAIL=mail@pasport-bezopasnosty.ru
```

Для порта 587 обычно требуется SMTP_SECURE=false (STARTTLS); используйте параметры именно вашего почтового провайдера. LEAD_EMAIL_FROM при необходимости задаёт разрешённого отправителя, иначе берётся SMTP_USER. LEAD_EMAIL_TO отдельно управляет мгновенными уведомлениями о новых заявках; ежедневное письмо использует DAILY_REPORT_EMAIL. Секреты вводятся только в терминале/VPS, не в переписке и не в Git.

После установки новой версии и сохранения SMTP выполните от root:

```bash
cd /var/www/pasport-bezopasnosty.ru/app/passport-security-base
bash scripts/install-daily-report.sh
```

Установщик проверит SMTP-соединение и авторизацию без отправки тестового письма и включит только ежедневный отчёт. Если SMTP не настроен, установка остановится до включения таймера. User/Group сервиса — passport. Таймеры нормативных напоминаний и мониторинга этим скриптом не включаются. Для обновления статуса SMTP в уже запущенном backend потребуется штатная перезагрузка процесса приложения после правки env.

Предпросмотр без отправки (из каталога проекта под passport):

```bash
npm run report:preview
```

Файлы появятся только в приватной data/daily-report-preview/. Не размещайте их в public или dist. Ручной запуск настоящего отчёта после настройки (от root, отправит письмо указанному получателю):

```bash
systemctl start passport-daily-report.service
systemctl status passport-daily-report.service --no-pager
systemctl list-timers --all passport-daily-report.timer --no-pager
```

## Проверки

```bash
npm ci
npm run qa
npm run format:check
npm run lint
npm run build:artifacts
npm run test:e2e:run
```

Добавлены серверные сценарии границ времени, приватности, перезапуска, конкурирующих действий, сбоя/повтора публикации и формирования письма без реальной отправки. Браузерные тесты — tests/e2e/article-scheduling.spec.js. Все проверки используют отдельные фикстуры, а не восстановленные статьи.
